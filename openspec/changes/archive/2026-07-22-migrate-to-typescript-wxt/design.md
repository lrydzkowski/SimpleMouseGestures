# Design: migrate-to-typescript-wxt

## Context

The extension is ~1,650 lines of vanilla JS in three Chrome contexts (content scripts, MV3 service worker, popup) with
no package.json, build step, or tests. Content scripts are plain non-module scripts loaded in a hand-maintained
dependency-order list in `manifest.json`; the service worker and popup are ES modules. The code is uniformly structured
as classes with `#private` members and constructor DI. Releases are built by hand and committed as zips to the repo
root. WXT was chosen over Vite+CRXJS (revived but smallest/least certain maintenance) and over a plain esbuild script
(no dev reload, no zip command, no cross-browser path) as the most actively maintained extension toolchain in 2026.

## Goals / Non-Goals

**Goals:**

- All runtime code in strict TypeScript, built by WXT, with runtime behavior identical to v0.8.0.
- Manifest generated by WXT with field-for-field parity for everything the current `manifest.json` declares.
- Vitest unit tests for the pure logic (gesture tokenization, serialization, operation resolution, backup validation).
- GitHub Actions workflow validating every push/PR and uploading a store-ready zip artifact on `master` pushes.
- Development workflow documented (README.md, CLAUDE.md).

**Non-Goals:**

- No behavior changes, new operations, or UI changes.
- No Firefox/Edge builds (WXT keeps the door open; not in this change).
- No E2E/browser tests (Playwright is a possible future change).
- No tests for Chrome-API-dependent layers (operations, storage classes, canvas, event wiring).
- No ESLint adoption.
- No automatic publishing to the Chrome Web Store; CI produces the zip only.

## Decisions

### D1: WXT project layout with `srcDir: 'src'`, auto-imports disabled

- `src/entrypoints/background.ts` — `defineBackground()`, wires current `service-worker.js` logic.
- `src/entrypoints/content.ts` —
  `defineContentScript({ matches: ['<all_urls>'], runAt: 'document_start', allFrames: true })`, wires current
  `content.js` composition root.
- `src/entrypoints/popup/` — `index.html`, `main.ts`, `style.css` plus the popup classes (current `popup/*.js`).
- `src/content-scripts/`, `src/service-worker-scripts/` (with `operations/`) — keep current folder and file names,
  converted to `.ts` modules; classes become `export class`.
- `src/shared/consts.ts` — `Consts` converted to a typed `as const` module, imported explicitly everywhere (replaces the
  global script). Shared types live here too (see D3).
- `public/icon/{16,32,48,128}.png` — moved from `images/`; WXT generates the manifest `icons` entries. Promo/screenshot
  images stay out of `public/` (repo-only assets, not shipped).
- WXT auto-imports are disabled (`imports: false` in `wxt.config.ts`): explicit ES imports match the project's "explicit
  over implicit" convention.
- Alternative considered: keeping source at repo root (WXT default). Rejected — config files and OpenSpec dirs would mix
  with entrypoints; `src/` keeps the tree legible.

### D2: Manifest via `wxt.config.ts`, verified against the current manifest

`wxt.config.ts` declares `name`, `description`, `author`, `version_name`, `permissions` (`scripting`, `storage`,
`sessions`), `host_permissions` (`<all_urls>`), and the popup action; `version` comes from `package.json`. Content
script options live in the entrypoint (D1). The generated `.output/chrome-mv3/manifest.json` MUST be diffed against the
current `manifest.json` as an explicit verification step — content-script `js` list and file paths will differ by design
(single bundle), everything else must match.

### D3: TypeScript conventions

- `strict: true`; project tsconfig extends the WXT-generated one (`wxt prepare` emits `.wxt/tsconfig.json`).
- Classes keep `#private` fields, constructor DI, early returns; no comments (target ES2022, native private fields).
- Typed domain model in `src/shared/`: `type Direction = 'up' | 'right' | 'down' | 'left'`, message union
  (`GesturesMessage | UpdateStorageMessage`), storage payload types (gesture map, `Settings` with
  `lineColor`/`lineWidth`), backup file shape.
- The storage key strings, currently duplicated across the three storage classes, move to one shared module. The three
  per-context storage classes themselves stay separate — their behaviors (caching/seeding vs. read-write/notify vs.
  read-only) differ deliberately.
- Chrome API types come with WXT's toolchain; code keeps calling `chrome.*` as today.

### D4: Coloris from npm

Replace vendored `popup/dependencies/coloris.min.{js,css}` with the `@melloware/coloris` npm package, imported from
`popup/main.ts` (JS + CSS). The vendored copy is minified and unversioned, so the implementation MUST verify that the
initialization options the popup uses exist in the installed package version before deleting the vendored files.
Fallback if the API drifted: keep the vendored files as a local module imported through the bundler and drop only the
`.prettierignore` special-casing.

### D5: Tests — Vitest with `WxtVitest`, black-box where possible

- Vitest with the `WxtVitest` plugin (from `wxt/testing`) and `happy-dom` environment; fall back to `jsdom` if synthetic
  `MouseEvent` fidelity (the `buttons` init property) proves insufficient in happy-dom.
- `GesturesHandler` is tested black-box: call `initPosition`, dispatch synthetic `mousemove` events with `buttons: 2`,
  assert `getGestures()`. No refactoring for testability — the event-driven surface is sufficient to cover angle
  boundaries (45/135/225/315), consecutive-duplicate dedup, the >3px movement threshold, and non-right-button ignore.
- `GesturesSerializer` and `OperationResolver` are pure lookups — direct unit tests.
- `BackupHandler` uses constructor DI — inject a fake storage object; cover export content and each import validation
  failure (version, gesture token count/values, unknown operation key, color regex, width bounds).
- Tests live in `tests/` mirroring source paths (`tests/content-scripts/gestures-handler.test.ts`, ...).

### D6: CI — one workflow, zip artifact on master only

`.github/workflows/ci.yml`, triggered on `push` (all branches) and `pull_request`:

1. checkout → setup-node (LTS, npm cache) → `npm ci`
2. `wxt prepare` + `tsc --noEmit` (WXT/Vite builds do not type-check)
3. `npx prettier --check .`
4. `vitest run`
5. `wxt build`
6. Only when `github.event_name == 'push' && github.ref == 'refs/heads/master'`: `wxt zip` and upload the zip from
   `.output/` via `actions/upload-artifact`, named with the package version.

Alternative considered: GitHub Release per version bump. Deferred — the user chose plain CI artifacts; a Release step
can be added later without redesign.

### D7: Unminified production build

Disable minification in the WXT/Vite build config. The Chrome Web Store forbids obfuscation and reviews are simpler with
readable output; at this code size the zip stays tiny either way.

## Risks / Trade-offs

- [WXT API surface drifts from this design (config keys, zip naming)] → Pin the WXT version in `package.json`; consult
  the installed version's docs during implementation rather than trusting this document for exact option names.
- [Generated manifest silently diverges from the current one] → Explicit diff step in tasks (D2); any mismatch beyond
  the content-script bundling is a defect.
- [Coloris npm package API differs from the unversioned vendored copy] → Verification step + vendored-as-module fallback
  (D4).
- [happy-dom does not model `MouseEvent.buttons`] → jsdom fallback (D5).
- [Framework lock-in: WXT owns manifest generation and project layout] → Accepted; source classes stay plain TS modules
  with no WXT imports outside `entrypoints/`, so a future bundler swap only touches entrypoints and config.
- [Dev workflow breaks for anyone loading the repo root unpacked] → Accepted and documented; README/CLAUDE.md update is
  part of the change.
- [Store review sees a fully re-bundled upload] → Unminified output (D7) and unchanged permissions keep the diff
  reviewable.

## Migration Plan

Single version branch (current `v0.8.0` flow), sequenced so the extension stays loadable at each step:

1. Scaffold WXT project (package.json, config, entrypoints) alongside existing files.
2. Move/convert sources to TS under `src/`; wire entrypoints; verify manifest parity and manual gesture smoke test.
3. Add tests; add CI; update docs; delete legacy root files (old JS tree, manifest.json, vendored Coloris, committed
   zips).

Rollback: revert the branch — the pre-migration tree remains fully functional from git history.

## Open Questions

- None blocking. Version bump (0.9.0) happens at release time per the existing convention.
